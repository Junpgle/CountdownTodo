# 第二轮方案：规划块可用时段推荐

日期：2026-10-07；实施验收更新：2026-10-08。状态：用户已明确批准“同意第二轮”；功能、反馈修复和界面重设计已实施；用户于2026-10-08回复“可以，继续下一轮”，第二轮验收通过。验收记录见 `docs/reports/2026-10-08-plan-availability-acceptance.md` 及界面重设计报告。

第一轮全局搜索范围筛选已通过用户验收。本轮继续连接项目的待办、课程、固定日程、规划块、历史估时和番茄钟，改善“知道要做什么，但还要自己找时间”的操作。

## 1. 建议与当前依据

在“添加／编辑规划块”面板中增加“找可用时间”。用户选择待办、日期、时长和可安排范围后，得到最多三条候选时段；选择候选只填入编辑器，仍须点击“保存规划”或“保存并开始专注”。

本轮阅读了项目架构、功能清单、待办时间语义、规划块说明，并检查了规划界面、课程调休、冲突检测、系统日历读取及持久化路径。当前源码显示：

- `TodoPlanScreen._loadData` 读取规划块、待办、分组、课程、标签、番茄记录；现有 `_AddPlanBlockSheet` 支持手动开始／结束时间和历史估时，没有本地可用时段推荐入口。
- `TimeEstimationService` 使用本地历史和规则估时，可复用为时长建议，不需要外部模型请求。
- `ScheduleConflictService` 已区分课程／固定日程的硬约束与规划块的软约束，并使用严格重叠判断；它目前没有查找空档，也没有规划块之间的冲突输出，不能直接当作完整的可用时间引擎。
- `CourseService.getAllCourses` 默认应用课程调休；推荐必须遵循这些实际发生日期，不能另写一套星期或学期推断。
- `DeviceCalendarReadService` 当前仅在 Android/iOS 支持读取，已有开关、授权检查与内存缓存；返回的系统日历事件保持只读、不入库、不参与同步。
- `getPlanBlocksByDay` 当前按开始日期读取，无法单独覆盖前一天开始、当天仍占用的跨日规划。推荐读取需要用区间相交条件。
- 部分现有读取接口遇到错误返回空列表。推荐需要可区分“确实没有安排”和“没有成功读到安排”的数据快照。
- 编辑器现有保存会直接修改打开时的规划对象。推荐路径保存应读取最新记录，并保护原记录版本，避免覆盖期间收到的同步修改。

以上是当前源码调研结论，尚未进行第二轮运行或性能验证。当前包版本仍为 `6.6.117`。

## 2. 用户收益与示例

例如在未来某天安排“复习高数”，用户指定需要 45 分钟、可安排时间为 08:00–22:00。当天课程占用 09:00–10:00，固定日程占用 11:00–12:00，已有规划占用 14:00–15:00，则候选可以是：

| 候选 | 推荐时段 | 依据 |
| --- | --- | --- |
| 1 | 08:00–08:45 | 第一段连续空档可容纳 45 分钟 |
| 2 | 10:00–10:45 | 课程结束后，下一项固定日程前 |
| 3 | 12:00–12:45 | 固定日程结束后，已有规划前 |

示例假定目标待办没有更早截止、没有其他日历占用。选择第 2 条后，编辑器显示 10:00–10:45；此时数据库、提醒和番茄钟都尚未变化。保存后才创建规划，待办自身截止日期不变。

## 3. 交互方案

### 入口及输入

- 入口放在现有添加／编辑规划块面板的开始／结束时间附近；日视图点击、拖选新增及已有规划编辑均共用同一入口。
- 初始折叠为“找可用时间”，展开后显示待办、推荐日期、需要时长、可安排时间范围及数据覆盖说明。
- 日期默认继承当前编辑器日期，可通过 `showAppDatePicker` 修改；查找范围为该本地自然日，不跨日创建推荐规划。
- 时长默认继承当前有效规划时长；无有效时长时为 30 分钟。提供 15／30／45／60 分钟快捷项和自定义正整数分钟输入，上限不超过查询窗口的实际长度。
- 历史估时作为可采用的建议，用户可以修改。估时算法保持现有实现；新面板称为“历史估时”，避免暗示正在调用外部 AI。
- 初始可安排范围为 08:00–22:00，可修改为当天任意合法区间；修改只用于当前草稿，本轮不增加全局工作时间或作息设置。
- 尚未选择待办、待办已完成／删除、时长不合法、窗口倒置或所选日期已过去时，显示具体原因，不发起推荐。
- 仅为新建及 `planned`／`reminded`／`delayed` 的已有规划提供推荐改期；完成、跳过、取消、漏做、正在专注的记录不提供此操作，不自动改其状态或实际执行数据。

### 展示及采用

- 点“查找时段”后显示加载状态，成功后按开始时间排序，最多三条候选；每段连续空档只取最早可行开始，避免同一空档被重复的紧邻候选挤满。
- 候选清楚显示日期、开始／结束和时长；不足三段时按实际数量显示。
- 选择候选更新草稿开始、结束、计划分钟数；不改备注、提醒偏好、番茄配置、待办截止时间，不直接保存或启动专注。
- 没有满足时长的空档时，显示“当天没有连续 45 分钟的可用时段”，可修改时长、日期或时间范围；不自动拆分、不延长截止、不移动其他安排。
- 后续手动改时间时转回手动草稿，推荐采用状态清除。手动拖动／缩放已有规划的原路径不在本轮改造范围内。
- 动态取色、主题及可选玻璃模式沿用共享组件；面板可滚动，键盘和较大字体下仍能到达候选与保存按钮。

## 4. 占用与时间规则

| 来源／条件 | 推荐计算规则 |
| --- | --- |
| 课程 | 当前账号本地可见的实际课程实例，沿用既有调休／假期规则；不同学期按真实发生日期纳入，去除删除和重复实例 |
| 固定日程 | 纳入有效开始／结束且未删除、未取消的记录；按相交区间读取，覆盖跨日记录。时间待定记录单独提示，不能猜测占用时段 |
| 已有规划块 | `planned`／`reminded`／`delayed`／`focusing` 作为占用；删除、完成、取消、漏做、跳过不占用。编辑时只排除当前规划的 UUID，其他同待办规划仍占用 |
| 普通待办 | 未安排、日期待办和截止点本身都不作为忙碌时段；不能把创建时间到截止时间算作占用 |
| 旧版实际时间区间 | 按既有 `hasLegacyTimeRange` 等兼容识别规则处理旧执行区间，并与已有实际规划去重；不自动迁移或重写旧待办 |
| 手机日历 | 仅纳入已开启且已授权读取的事件，使用提供方给出的实际区间；全天事件按其日期区间占用，跨日事件裁剪到查询日。瞬时事件沿用读取服务现有的一分钟规则 |
| 日期待办截止 | 以该截止日期次日零点为上界，允许当天内完成，不误用旧存储中的午夜作截止点 |
| 定时待办截止 | 候选结束不得晚于其明确截止时刻；无截止则使用用户选择的查询窗口 |
| 已过截止 | 显示“截止前已无可用时段”，不偷偷延长截止；用户仍可以返回原手动编辑流程自行决定 |
| 今天 | 查找起点不早于当前时间，向上对齐到下一分钟；选择与保存时再次核对时间，避免保存已经过去的候选 |
| 相邻区间 | 使用半开区间 `[开始, 结束)`，09:00–10:00 与 10:00–10:45 不算重叠；本轮不额外加入通勤或休息缓冲 |

候选是“在已检查来源中没有占用”，不能保证服务器尚未同步的日程或其他设备日历不存在。数据覆盖说明用于明确这一实际边界。

## 5. 数据不完整时的行为

- 推荐通过当前账号的本地数据完成，不要求联网、不调用外部 AI。网络离线仍可根据已有本地记录查找；不宣称本地记录是最新云端全量。
- 课程、固定日程、规划块等应用内来源读取失败时，显示具体来源失败和重试入口，不生成假空闲候选。必要的读取接口增加显式错误状态，原调用方默认行为保持兼容。
- Android/iOS 手机日历未开启或未授权时，说明“未计入手机日历，仅检查应用内安排”；本功能不会自动打开设置或发起权限请求。
- 手机日历已开启但查询失败时，默认停止本次推荐；用户可重试，或明确选择“仅按应用内安排查找”。采用后仍保留该覆盖说明，保存按同一明确范围复查。
- macOS、Windows、Web 沿用当前系统日历读取不支持的事实，仅检查应用内安排，不引入新平台桥接代码。
- 时间待定日程、无法解析的课程时间等不能当成正常空档数据静默忽略：显示未能确定时间的记录数量及查看说明，不推断其时间。
- 系统日历只在内存中作为占用信息，不将其标题、地点或事件写入应用数据库、oplog、同步 payload 或日志。

## 6. 异步与保存策略

### 防止响应覆盖

绑定账号、待办 UUID、日期、时长、查询范围、编辑记录 UUID、数据覆盖选择及递增请求序号。只有最新请求能展示候选或结束加载；关闭面板后不更新状态。

修改输入、应用内相关数据刷新、课程调休配置变化、手机日历开关变化或应用恢复前台时，旧候选失效，重新查找后才能以推荐方式采用。保存仍重新读取，刷新监听不是唯一保护。

已有历史估时响应也必须校验待办与草稿修改序号；用户改过时长或采用推荐后，旧估时不能再次覆盖结束时间。初次自动估时与手动选择的边界一起测试。

### 保存与开始专注

- 推荐填入路径点击“保存规划”或“保存并开始专注”，先重新核对当前账号、目标待办状态、候选时间和占用来源，再保存。
- 手机日历已纳入时，保存前绕过旧内存区间缓存重新读取；可为 `readEvents` 增加默认关闭的强制刷新选项，保留其他调用方现有缓存行为。
- 新占用或读取失败出现时不自动换时段、不写入规划、不启动专注；保留草稿并提示重新查找／返回修改。
- 编辑记录被同步修改、删除或转入正在专注／历史状态时，不把打开时的对象覆盖回去；提示读取最新记录后重新编辑。
- 新增编辑器专用的条件保存入口：在本地事务中校验编辑记录版本／更新时间及最新数据库占用，写入规划与原有 oplog；保存后复用现有同步请求和范围刷新事件。课程调休配置在保存前加载并核对变更状态。其他同步导入路径不套用这个编辑器交互规则。
- 复制最新记录，仅更新用户编辑字段，保留 UUID、实际专注秒数、关联番茄记录、外部日历 ID、同步元数据等。数据库写入失败时保留草稿，不能给出成功提示。
- 防重复点击：一次确认只创建／修改一个规划；“保存并开始专注”只有保存成功才调用已有 `PomodoroControlService`。启动失败时说明“规划已保存，专注未启动”，不得再建一条规划。
- 系统日历和远端设备无法被本地事务锁定，本轮不是跨端原子预订。保存后仍使用项目已有同步／冲突机制处理后续变动。

本轮保护推荐填入的保存流程。原手动拖动、边缘缩放、AI 批量排程及全局同步策略不扩展为自动调度系统。

采用“有状态数据快照 + 纯区间计算 + 共享候选面板”，业务规则不全部堆在现有大页面中。

## 8. 验收标准

| 场景 | 必须证明的结果 |
| --- | --- |
| 基本推荐 | 示例课程／固定日程／规划占用后，返回精确 45 分钟候选，候选数量、排序与空档相符 |
| 边界计算 | 重叠及包含区间合并；相邻区间合法；恰好等于所需时长可用；零长／反向区间、满日占用与空集合均有明确结果 |
| 跨日与状态 | 前一天开始的规划／固定日程、跨午夜系统事件、全天事件不漏掉；计划状态过滤正确；编辑只排除自身 UUID |
| 课程实际日期 | 调休、假期、多学期真实日期与已有课程规则一致；不出现幽灵占用或遗漏实际课程 |
| 待办语义 | 日期待办不占一天，截止点不占区间；截止上界正确；旧执行区间保持兼容且不会重复占用 |
| 账号与来源失败 | 两个合成账号不会混用；应用内读取失败没有假候选；外部日历缺失显示覆盖范围；部分来源继续必须由用户明确选择 |
| 采用与取消 | 点候选只改草稿；取消无规划、oplog、提醒或专注写入；原待办截止保持不变 |
| 异步乱序 | 日期 A→B→A、快速改时长／待办、关闭面板、估时晚返回、同步刷新、日历设置变化，旧请求均不能覆盖新状态 |
| 保存复查 | 已选时段被新安排占用后保存失败且无副作用；日历复查绕过旧缓存；目标待办状态与编辑记录版本变化均有明确处理 |
| 保存完整性 | 一次确认仅有一条规划及对应写入记录；旧实际执行／日历关联不丢；数据库失败不提示成功；双击不重复创建 |
| 保存并专注 | 校验失败时零启动；保存成功后才调用原启动路径；启动失败时不重复保存或丢失已保存规划 |
| 所有入口 | 日视图点击新增、拖选新增和已有规划编辑都能使用同一功能；手动时长、提醒、番茄设置及返回行为无回归 |
| 界面 | 窄屏320／390、横屏带键盘、桌面宽屏、字体1.6／2.0、深浅色及玻璃开关下控件可达、无溢出，状态不只靠颜色 |
| 性能和隐私 | 使用合成数据记录快照读取与纯计算的实际耗时；记录查询范围／次数；不访问个人日历、日记或账本作为样本，不预先承诺性能比例 |

计划按以下顺序执行与交付：

1. 建立纯区间计算与边界测试，确定来源状态和当前时间注入。
2. 加入隔离数据库及模拟 MethodChannel 的读取／条件保存测试，检验跨日、账号隔离、事务／oplog及失败行为。
3. 接入共享面板和三类编辑器入口，测试采用、取消、乱序、估时及两种保存按钮。
4. 运行改动文件格式化、静态分析、相关聚焦测试和 `git diff --check`；回归现有 `schedule_conflict_service_test.dart`、日历同步及相关课程日期测试。以实际仓库存在的测试路径为准，不宣称未跑套件通过。
5. 用实际编辑器与合成数据运行可见验收，覆盖候选选择、取消、持久化、返回和窄／宽布局；有可用测试设备时验证平台日历模拟或测试账号路径。未完成的真机／完整应用路径单独列出。

## 9. 风险与本轮边界

- **错误空闲会误导安排**：应用内严格读取、来源覆盖说明和保存前复查为必须项，不能用成功空列表掩盖错误。

- **面板变长**：将推荐区做成可展开且滚动的共享控件，验证大字体／键盘和三个真实入口。
- **推荐被并发修改推翻**：请求序号、刷新失效、最新记录与事务条件保存共同处理；明确手机日历／跨端更新无法原子锁定。
- **范围扩大**：本轮是单个待办的连续时段推荐，不自动拆分、不批量重排、不移动课程／固定日程、不改 AI 工具协议、不添加全局工作时间设置、不开发新的原生日历读写能力。
