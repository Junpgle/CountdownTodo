# 第41轮方案：固定日程详情直接新建关联待办

日期：2026-10-24（北京时间）

状态：**已实现并完成技术验收，等待用户确认验收**

## 1. 问题与建议

打开考试、面试或预约的固定日程详情后，用户可以查看关联待办，也可以打开选择页关联一条已经存在的待办；但没有从当前日程直接新建准备事项的入口。用户需要离开日程、先创建待办，再返回日程搜索并关联，步骤容易中断，也容易忘记最后一步。

建议在固定日程详情的“关联待办”区域增加“新建关联待办”。沿用现有待办表单，并在保存时把新待办与当前日程场次的关系一并写入本地 SQLite 事务。保存成功后，详情立即显示新任务；若日程在编辑期间发生变化，整笔事务拒绝提交，表单内容保留。

这是当前场次的单次关联操作。它不会把一个新任务复制到整个重复日程系列，也不会自动创建规划块或改动固定日程时间。

## 2. 当前实现依据

- `FixedScheduleDetailScreen` 已展示关联待办；空状态按钮“添加关联待办”会进入 `FixedScheduleEditorScreen`，再由其中的 `FixedScheduleRelatedTodoPickerScreen` 选择已有待办；没有从详情上下文直接新建并关联的流程。
- 固定日程关系唯一存放在 `FixedScheduleItem.relatedTodoIds`／`related_todo_ids` 中，可继续复用，不需要新字段或迁移。
- `AddTodoScreen` 已有待办标题、备注、期限、提醒、团队选择和退出草稿保护。它的 `onManualTodoSaved` 会在表单关闭前保存待办，且同一编辑会话的 `_pendingManualTodoId` 能稳定重用待办 UUID。
- `StorageService.saveTodos` 和 `saveFixedSchedulesIfUnchanged` 各自已有事务、op log 和并发快照保护；新流程应把新待办行、固定日程关系变动和两条 op log 合并到一个本地事务，避免先成功一半。
- 固定日程详情由首页日程、今日规划、课程／日历和冲突复核等多个入口打开。新建能力应经过共用详情 UI，并为可写入口接入既有待办保存后的提醒、设备同步及小组件更新流程；只读冲突复核入口保持只读。

## 3. 批准后的用户行为

### 入口与表单

1. “关联待办”为空时显示两个清晰入口：“新建准备待办”和“关联已有待办”；已有列表时在标题行提供同样的新增入口。
2. 新建进入整页待办表单，不用浮层。表单顶部展示日程标题、日期和时间，并明确标注“只关联当前场次”。
3. 标题留空让用户自行填写；不自动猜测期限。用户可在标准期限控件中选择或清除期限，日期待办仍按自然日语义处理。
4. 日程属于团队时，新待办默认归属同一团队；个人日程创建个人待办。表单不得允许创建到另一团队后仍静默建立跨团队关系。分组默认不选，提醒沿用待办现有默认规则。
5. 此入口创建一个普通、未完成、非重复待办。需要重复待办时，用户仍从通用新增入口创建，再通过现有关联选择页按需关联；不会把一个单次日程关系扩展成重复系列关系。
6. 退出、取消或放弃草稿时，不写待办、固定日程或 op log；沿用 `AddTodoScreen` 已有的退出保护。

### 保存与反馈

1. 点击保存时，按当前会话账号确认固定日程快照仍有效、未删除，且待办与日程的团队范围一致。
2. 在同一个 SQLite 事务内插入待办、把新待办 UUID 去重加入当前固定日程的 `relatedTodoIds`，并分别写入待办与固定日程现有 op log。保持既有版本、更新时间、`sync` 参数和用户会话校验规则。
3. 事务成功后沿用现有待办保存后的提醒、团队状态、小组件和数据刷新流程，同时触发固定日程刷新与同步。详情更新成本场次的新关联列表。
4. 如果日程快照已变化、账号已切换、待办团队不匹配或任一写入失败，事务整体回滚：不能留下无关联的新待办或指向不存在待办的日程 ID；表单保留输入并显示可读错误。
5. 同一表单的重试继续使用同一待办 UUID。关系使用集合语义，不能重复加入相同 ID。
6. 已有重复日程仅修改当前场次的 `relatedTodoIds`；更早和更晚场次保持不变。新建重复待办、自动批量生成每场待办、规划推荐和 AI 批量创建不属于本轮。

## 4. 数据、安全与兼容边界

- 复用 `TodoItem`、`FixedScheduleItem.relatedTodoIds`、账号数据库和两类现有 oplog，不修改服务端、同步能力协商、Cloudflare 兼容路径或数据库 schema。
- 复用待办保存的 LWW、团队和账户会话规则；固定日程必须以详情读取时的完整快照做 CAS 校验，避免覆盖并发改期、取消、转团队或其他关系改动。
- 关系写入只关联当前固定日程 UUID，不级联改动其他场次。不要自动完成任务、改变其期限／提醒、创建规划块，或改动专注／投入记录。
- 如果团队权限读取失败或用户在保存期间切换账号，安全失败并保留草稿；不得用个人入口缓存展示或关联团队数据。
- 共享日程与待办须保持相同团队范围；个人日程只连接个人待办。已取消日程不提供“新建准备待办”快捷入口，但仍可通过既有编辑路径处理历史关系。
- 本轮不处理手机日历来源事件的写回，也不自动关联来自外部日历的全部重复场次。
- 不触碰当前工作区中 Android 到课提醒、财务页面和 `pubspec.yaml` 版本改动。

- `lib/screens/add_todo_screen.dart` 及其 `TodoSectionWidget` 契约（或一个窄范围适配器）：支持仅用于单次关联待办的上下文模式，保留现有普通新建流程和退出保护。
- `lib/storage_service_todos.dart`、`lib/storage_service_fixed.dart`、`lib/storage_service.dart`、`lib/storage_service_contract.dart`：在待办写事务内校验并更新一个固定日程快照，合并写两张表和各自 op log；返回更新后的日程快照。
- `lib/screens/home_dashboard_persistence.dart`／相关详情路由：把共用的保存后提醒、小组件和团队更新流程提供给关联新建入口；冲突复核等只读详情不显示该动作。
- `test/services/`：测试双实体事务成功、写入失败全回滚、日程并发变化拒绝、团队错配拒绝、UUID 重试幂等和重复日程仅影响当前场次。
- `test/screens/` 或 `test/widgets/`：覆盖空态／已有列表入口、团队预选、编辑退出保留、取消零写入、保存后详情刷新和窄屏布局。

## 6. 验收标准

1. 详情无关联项和已有多条关联项时均能进入“新建关联待办”；“关联已有待办”原流程继续可用。
2. 新建页显示正确的固定日程标题、日期、时刻和“只关联当前场次”；初始期限为空，团队归属与日程一致且不能误选跨团队。
3. 取消或放弃时待办表、固定日程表和 op log 均无写入，退出保护保留所有未保存输入。
4. 保存成功时待办与当前场次关系同时存在，两个 op log 正确；关系 ID 不重复，详情显示新任务，数据刷新和现有提醒／设备更新流程均执行。
5. 事务中途失败、账号切换、团队范围变化或日程快照过期时，待办与固定日程两边都不写入，输入仍可重试。
6. 重试不会产生重复待办或重复关系；重复固定日程只修改当前 UUID，其他场次关系和重复规则不变。
7. 日期待办使用自然日语义；默认不生成任何推断期限、规划块、专注或时间日志。
8. 自动化测试覆盖存储事务和用户流程；变更文件静态分析、格式检查、`git diff --check` 与 Web release 构建通过。全量测试如有失败，应调查真实原因并原样报告，不删除旧测试绕过失败。
9. 提供“无关联日程详情”和“新建上下文表单／保存后关联”手机截图，注明来自 WidgetTester、浏览器或真机的真实来源；另检查深色、大字和窄屏。
10. 报告明确区分 SQLite／同步队列测试、提醒与小组件调用验证、Web 构建以及尚未覆盖的真机和跨设备同步。
