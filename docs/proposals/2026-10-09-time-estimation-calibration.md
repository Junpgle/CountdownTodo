日期：2026-10-09（北京时间）。用户回复“同意”批准实施，并于2026-10-10回复“确认通过”。状态：**实现及用户验收均通过**；结果见[第六轮验收报告](../reports/2026-10-10-time-estimation-calibration-acceptance.md)。

第五轮已由用户确认“通过”。本轮结合待办新增、首页编辑待办进入规划、专注记录及规划查找这几条流程，改进它们共用的估时能力。

## 1. 要解决的问题

你此前要求“先按AI预测完成时间找空闲，不要先按30分钟”。当前规划入口已经等待估时后再找推荐，但估时依据本身还有偏差。

本次直接检查了当前源码，而不是采用旧ML规划文档里的未完成清单：

| 当前实现 | 对体验的影响 |
| --- | --- |
| `TimeEstimationService`将没有实际投入的规划块，用`planned_minutes`作为历史耗时 | 还没做的安排也能影响下一次估时，形成“自己预测、自己验证”的循环 |
| 番茄记录缺少实际时长时，使用计划轮次时长 | 预定25分钟可能被当成真实做了25分钟 |
| 样本按标题去重，只保留最近一条 | 同名任务的多次经验丢失；一项任务做了多个番茄，也可能只剩一个轮次的时长 |
| 相似度层没有匹配时返回0，但仍分配固定权重 | 有历史却没有相似任务时，结果可能被零值压低 |
| 标签分组使用字符串包含判断，部分记录缺少待办关联 | 容易把不同标签误当成同类，分类参考不稳定 |
| 新建待办显示置信百分比，规划只显示分钟数 | 用户看不出是历史支持还是粗略猜测，也容易把分数理解为准确率 |

目前的估时是本地历史统计、标题相似度与关键词规则的组合，没有调用远程大模型。本轮沿用本地计算，不增加AI调用、费用或上传。

以上为方案调研阶段的源码结论。批准后已建立四项失败复现并修复；验证明细见验收报告，不将回归通过视为真实任务预测准确率。

## 2. 用户看到的变化

### 保持紧凑的主界面

新建待办和新建规划统一展示类似：

```text
预计专注用时 60分钟 · 历史参考较充分   ⓘ
```

资料不足时显示：

```text
预计专注用时 30分钟 · 参考较少，可调整   ⓘ
```

这里的30分钟只是一个可能的关键词估算结果，不恢复“先用30分钟寻找，再等估时覆盖”的旧流程。已有待办进入整页规划仍先完成估时，再展示两个推荐；自定义查找弹窗仍默认五个候选，并沿用账户避让偏好。

主表单不新增解释卡片、图表或长列表。点击信息入口才打开紧凑的只读“估时依据”弹层：

- 当前建议分钟数，以及“历史参考较充分／一般／较少”。不显示貌似准确率的百分比。
- 本次实际使用的样本数量与范围，例如“参考3个相似的已完成待办，累计专注分别为50、60、65分钟”。同名的不同待办仍分别计数。
- 最多展示3组相似标题和耗时概况；更多同名样本用数量概括，不展开全部历史。
- 数据不足、分布差异大或读取失败时，说清原因；没有真实依据时不展示虚构相似任务。
- 一句说明：“参考的是已记录的专注投入，不包含休息或未记录的工作；不代表当前待办剩余时间。”

继续允许用户手动改时长、选择其他时段。不自动修改待办截止时间、番茄轮数或已采用的时间段。

### 两个具体例子

1. 某个已完成待办分三次专注，每次实际25分钟：历史样本是这个待办累计75分钟，而不是最近一轮25分钟，也不是重复计入规划汇总后得到150分钟。
2. 用户先安排了180分钟但尚未执行：这条安排不成为“真实做过180分钟”的估时依据。没有可靠历史时，明确显示参考较少，仍可手动调整。

## 3. 历史样本怎么计算

### 以具体待办实例为单位

- 只使用当前账号中已完成、未删除、没有同步冲突的真实待办作为完成样本。
- 一条具体待办UUID形成一个样本。一个待办的多次有效专注先累加；相同标题的不同UUID不合并。重复待办的每期实例分别统计，不把整个系列累计当作单次耗时。
- 专注记录优先按明确的`todo_uuid`归属；只有没有直接待办绑定时，才允许通过有效`plan_block_id`关联到同账号待办。两种关系指向不同待办时排除该记录，不按标题猜归属。
- 每条专注记录UUID只使用一次；规划块的`actual_focus_seconds`是汇总缓存，不与明细相加。本轮不使用缺少明细的旧汇总去制造高参考程度的样本。

### 使用明确的实际投入

- 只累计明确记录的、有限且非负的`actual_duration`，按秒累加后统一转换分钟；0是已知零投入，不能回退成计划时长。
- 已结束或放弃的专注，若有有效实际投入，可以计入后来已经完成的待办总投入。放弃一次番茄不等于这段实际工作没有发生。
- 删除、冲突、尚未结束、未来或时间结构无效的记录排除；实际时长明显超过合法墙钟区间的异常记录排除。已知暂停时间不再扣第二遍。
- 某待办仍有相关非删除专注缺少实际值、存在身份冲突或无效时长时，将该任务标记为记录不完整，不作为校准样本；依据中说明可用历史不足。
- 未完成待办的部分投入、自由专注、未关联时间日志、课程、手机日历与计划分钟数不当作“一个任务已完成的耗时”。不靠同名将时间日志自动归入待办。

本轮不会删除、修补或重写任何历史记录，也不修改专注统计中既有兼容口径。估时输入采用独立的明确实际值规则，避免牵连现有统计、通知、同步与完成判定。

## 4. 估算与参考程度

- 保留现有中文／英文标题分析与关键词冷启动能力，优先参考足够相似的已完成任务，其次参考同分组／精确标签的任务。
- 相似样本保留其UUID、时长和时间，直接用这条样本参与计算；不再按标题二次寻找“第一条”。弱相似不包装成相似任务依据。
- 采用对离群值更稳健的中位数类统计，结合近期权重；少量异常长任务不把一般任务估到数小时。记录很少或差异很大时，降低历史影响并明确提示。
- 没有匹配的层不参与加权，将其余有效层的权重归一化；不把“缺少数据”当作0分钟。全部没有可靠历史时，回退关键词估算。
- 标签按解析后的UUID集合精确匹配，不使用字符串包含。分组归属在同一账号数据快照中读取。
- “历史参考较充分”至少要求5个有效相似完成样本，同时满足近期、相似程度和分布稳定条件；3～4个稳定样本最多显示一般；0～2个或差异明显最多显示较少。最终阈值与算法常量写入服务并用边界测试锁定。
- 参考程度表示依据的数量、相关性和一致性，不承诺完成概率或预测准确率。样本数量显示实际参与本次计算的数量，而不是账号全部记录数量。

不在本轮实现“总估时减去已投入等于剩余工作量”；专注时间不等同于成果进度。也不自动拆分长任务或增加番茄轮数。

## 5. 查询、状态和操作保护

- 查询先按待办聚合再限制样本数量，最多保留500个近期有效任务样本；不能先截取若干番茄再把某个任务的一半记录误称为累计总量。
- 使用现有账号数据库和索引做聚合、精简投影与批量关联，不把全部历史解码成Dart记录对象，不逐个任务发起查询。
- 估时读取采用一致的本地快照，捕获账号并在返回前复核。读取失败与确实没有历史分别表示，不能把数据库故障说成“没有做过”。
- 保留新增页500毫秒防抖，为标题、分组、账号及页面生命周期增加请求序号保护。旧结果不得覆盖新输入；切账号、离页、清空标题后不展示旧依据。
- 规划页继续保留草稿版本保护。用户已手动改时长、番茄或采用候选后，晚返回的估时不覆盖输入。读取失败提供可调整的粗略参考，草稿保留。
- 相关数据更新后，下次估时重新读取；打开依据弹层只展示当前结果快照，不额外触发一轮预测或修改输入。
- 估时和查看依据均只读，零规划写入、零待办写入、零oplog、零日历读写、零远程请求。同步继续使用现有路径。

## 7. 验收标准

1. 增加任意数量的未执行规划或仅有计划时长的番茄，不改变已有可靠样本和对应估时结果；不会从自己的推荐反向学习。
2. 同一已完成待办三次实际25分钟形成一个75分钟样本；同名不同待办分别计数；重复系列各期独立；规划缓存与番茄明细不重复计入。
3. 0实际值、缺实际值、删除、冲突、未结束、异常时长、未来、关联矛盾、空标题及跨日记录有明确规则与测试。已记录的跨日专注按完整有效实际值累计，不按某个日历日截短。
4. 标签UUID精确匹配；无相似任务的层不拉低结果；少量离群值不会把稳定的50／60／65分钟样本群拉到数小时。少样本不显示较充分。
5. 页面解释中的样本数、标题与耗时来自本次参与计算的快照；无数据、记录不完整和读取失败可区分；不展示伪准确率。
6. 首页编辑待办进入规划仍先估时、后显示两个推荐；自定义弹窗保留五个候选和记忆避让，用户手动时长／番茄／已选时段不被晚返回结果覆盖。
7. 新增页快速改标题、改分组、清空、账号切换或离页时，旧结果与旧依据不会出现；规划页沿用同等保护。
8. 估时和查看依据零写入，其他业务数据逐字段不变；采用估时仍只填草稿，显式保存才沿用既有校验流程。
9. 320／390窄屏、720×360横屏、桌面、1.6／2.0字号、键盘、深浅色、普通／玻璃下可操作无溢出；主表单保持紧凑，全天24小时一屏和拖动新建不变。
10. 执行新增算法／SQLite／界面测试及规划、第三轮恢复、第四轮改期、第五轮撤销的聚焦回归；相关分析、格式、差异检查通过，交付实际合成预览及报告。实机、全仓检查和真实同步分别说明验证边界。
