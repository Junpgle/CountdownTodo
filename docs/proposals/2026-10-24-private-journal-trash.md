# 第47轮方案：私密日记回收站与照片保留恢复

日期：2026-10-24（北京时间）

状态：**实现与本地验收已完成，等待用户验收；尚未提交 commit。**

规划模型：当前执行环境无法读取模型型号或思考强度。按此前你允许当前模型起草方案的授权完成本稿；不声称使用了 GPT‑6.1 sol／中。

## 1. 建议与收益

把日记详情里的永久删除改成可恢复的“移入回收站”，并提供一个本机回收站让用户恢复或逐条永久删除。日记文字和照片在回收站期间都保留。这样误操作可以恢复，也不会把私密内容上传到云端。

## 2. 代码现状与依据

- `lib/features/journal/screens/journal_detail_screen.dart` 的删除确认写着“删除后无法恢复”，确认后调用 `JournalStorage.deleteEntry`，随后立即删除照片文件。
- `lib/features/journal/services/journal_storage.dart` 的 `deleteEntry` 先删除 `journal_attachments` 行，再物理删除 `journal_entries` 行；日记的文字、附件关系和记录均无法恢复。
- `lib/services/database_helper.dart` 的日记表已经有 `journal_entries.is_deleted`，默认值为 0；当前 `JournalEntry` 模型和日记存储尚未用它实现回收站。
- `JournalMediaService.cleanupOrphanedMedia` 通过数据库附件路径集合判断哪些文件仍被引用。若移入回收站时保留附件行，现有清理流程就能继续保护这些照片。
- 记账和待办均有回收站入口；日记目前没有对应页面或日记存储回归测试。日记本身按账号存储在本机，不走云同步。

## 3. 批准后的用户流程

### 3.1 移入回收站

- 日记详情的删除动作改为“移至回收站”，确认文案说明文字和照片仍保留在本机，并可在回收站恢复。
- 确认后只把指定账号数据库中指定日记的 `is_deleted` 设为 1，并更新时间；不删除附件行或照片文件。
- 返回时间线后立即刷新，并提示“已移入回收站，可恢复”。取消确认时不改动任何数据。

### 3.2 回收站与恢复

- 日记首页提供清楚的“回收站”入口及当前条数。
- 独立回收站页按最近移入时间排列，展示日期、标题、正文摘要和照片数量；内容仍在本机显示，不提供分享或联网操作。
- 用户可逐条恢复。恢复使用原日记 UUID，将 `is_deleted` 改回 0；原日期、文字和附件关系不变，照片继续通过现有本地文件或 Web 数据库附件显示。
- 回收站为空时显示简短说明；加载或恢复失败时保留条目并提供重试。

### 3.3 永久删除

- 每条回收站项目都提供独立的“永久删除”，再次确认时展示标题、日期和照片数量。
- 取消不修改数据；确认后只删除该日记和其附件数据库行，再清理这篇日记引用的照片文件。
- 文件清理失败不伪装成日记仍可恢复；数据库记录已删除时，现有账号范围的孤立媒体清理会在后续日记加载时清理遗留文件。
- 本轮不提供“清空全部”、批量永久删除、自动按天清理或回收站跨账号操作，降低误删范围。

## 4. 存储与并发保护

- 复用现有 `is_deleted` 字段；不新增字段、表或数据库版本迁移。`JournalEntry` 模型增加删除状态，`fromMap`／`toMap` 与复制操作保持一致。
- 普通时间线和普通详情只读取 `is_deleted = 0`；回收站只读取 `is_deleted = 1`。每次查询、恢复或永久删除都绑定当前账号和具体 UUID。
- `saveEntry` 在事务内复核记录仍处于活动状态。若编辑器打开后该条目已移入回收站，旧编辑器不能通过保存悄悄将 `is_deleted` 改回 0；保留编辑草稿并提示用户先从回收站恢复。
- 恢复和永久删除也在事务内复核当前删除状态。重复点击、旧页面或过期对象不能改变另一条记录。
- 移入回收站和恢复都是软删除状态变化；附件行继续引用原始媒体。永久删除才会解除引用并调用已有媒体清理逻辑。
- 保持日记完全本机、按账号隔离的属性；不接入云同步、不改备份格式、不把日记或照片发给任何服务。

1. 删除确认取消后，活动日记、附件行和文件均不变；确认后日记从活动时间线消失并出现在本账号回收站。

3. 恢复后同一 UUID、原时间、正文和照片回到活动时间线；重复恢复不会创建副本。

5. 已移入回收站的旧编辑器不能覆盖删除状态；存储错误时保留可恢复数据并显示明确失败状态。
