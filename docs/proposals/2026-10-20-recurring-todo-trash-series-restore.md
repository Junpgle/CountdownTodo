# 第27轮方案：回收站重复待办整组恢复

日期：2026-10-20（北京时间）

状态：**已通过验收**

验收记录：[2026-10-20-recurring-todo-trash-series-restore.md](../reports/2026-10-20-recurring-todo-trash-series-restore.md)

## 1. 建议与收益

第26轮支持按本期、后续或整个重复系列移入回收站，但回收站仍只有逐条恢复。误删一个系列后，用户需要重复操作许多次；恢复过程中若保存失败，也会留下只恢复了一部分的系列。

建议为完整进入回收站的重复系列增加“恢复整组”操作：一次预览并恢复回收站中该系列的全部现存期次，保留各期原有的完成／跳过状态，并恢复其原有重复规则。以一个 SQLite 事务提交整组变更，失败时整组仍留在回收站。

## 2. 当前源码证据

| 位置 | 当前行为 |
| --- | --- |
| `lib/services/todo_recurrence_delete_service.dart` | 删除整个系列时保留重复规则在一条待办记录上，所有未删除期次改为软删除；本期和本期及以后则可能把规则转给保留期或收口结束日期。 |
| `lib/screens/historical_todos_screen.dart` | 回收站操作逐条读取最新记录，只将该记录的 `isDeleted` 设为 `false` 后单条保存；已失效文件夹会改为未分组。 |
| `lib/storage_service_todos.dart` | `saveTodos` 已提供 SQLite 事务、版本基线和重复系列成员校验；系列成员校验目前只对比活动记录，整组恢复还需覆盖已删除成员集合。分页读取补齐逻辑目前也只会从活动规则找系列，整组删除后需要补齐已删除规则承载项对应的系列。 |
| `lib/storage_service_todos.dart` | 周期维护将用户主动删除的确定性期次作为持久墓碑保留；显式恢复应由用户操作触发，不能依赖后台维护复活。 |
| `test/widgets/history_and_messages_ui_test.dart` | 已有逐条恢复的并发保护测试，可作为保留行为的回归基线。 |

## 3. 产品行为

- 回收站中按重复系列折叠展示该系列的已删除期次摘要，显示待办标题、回收站期次数、日期范围、已完成数和已跳过数；展开后仍可逐期使用原有“恢复待办”操作。
- 仅当从本机持久化数据读取后确认：该系列所有现存期次都在回收站、至少有两个不同日期的期次，并且恰好有一条记录保留非空重复规则时，显示“恢复整组（N期）”。一个规则都没有、规则重复、成员归属不清或系列仍有活动期次时，不提供批量入口，逐期恢复保持可用。
- 点击后展示确认摘要，明确恢复的是“回收站中的全部 N 个现存期次”，包含完成／跳过数量和日期范围。已被彻底删除的记录不在恢复范围内，也不声称可以找回。
- 确认后只清除这些现存期次的 `isDeleted`；保留标题、备注、日期、文件夹、完成／跳过状态和其余字段。唯一规则承载项恢复后，系列沿原规则继续；不额外改动其他系列或创建历史期次。
- 保存成功后刷新回收站、主页、搜索、提醒和现有同步链路；保存失败时不从列表移除任何行，说明失败原因并允许重试。重复点击在操作结束前禁用。
- 若某些记录引用的文件夹已失效，沿用单条恢复语义，将对应待办恢复为未分组，不因一个失效文件夹阻止其余期次恢复。

## 4. 界面方案

- 只调整回收站分区；普通待办仍逐条显示，历史、跳过和待修复列表不变。
- 重复系列默认折叠，行内摘要占用一行；展开后列出各期的日期与完成／跳过标记，保留每期现有操作。
- 可安全整组恢复时，在系列摘要上只放一个次要“恢复整组”入口，避免每个期次重复出现批量按钮。操作使用确认页／对话框，列出恢复数量和范围；使用当前主题色彩并适配窄屏、深色模式和大字设置。
- 搜索继续匹配标题和备注；命中系列中的任一期时显示匹配期次，并在摘要中说明当前是搜索结果，批量恢复的数量仍以完整系列实时预览为准。

## 5. 存储、并发与同步

- 新增重复系列恢复计划／预览服务；使用 `recurrenceSeriesId`（兼容仅规则承载项带系列 ID 的旧数据）找出全系列现存记录。读取需绕过当前列表分页，不能用屏幕上已加载的行数推断完整成员；调整分页读取，在 `includeDeleted` 模式也会从本页已删除规则承载项发现系列并补齐全部成员。
- 用户确认前展示实时计划；执行时重新读取系列及其成员，在同一事务内核对所有成员 ID、删除状态、版本和唯一规则承载项。成员在预览后新增、恢复、删除或编辑时，拒绝整组写入并要求重新加载，不允许部分成功。
- 对应保存事务应验证该系列**全部现存成员（包括已删除记录）**的集合与计划完全一致；复用现有版本基线和 oplog 原子写入，必要时扩展现有系列成员校验以覆盖回收站行。
- 只将本次明确选择的系列成员从回收站恢复；清理无效文件夹引用的规则与现有单条恢复一致。成功后清除本机同系列对应的用户删除墓碑例外，防止周期维护将刚恢复的记录继续按删除处理；其他日期的删除墓碑不受影响。
- 不增加服务端字段，不改 Alibaba 生产／调试端或 Cloudflare Worker，不部署。同步仅报告本地保存和现有同步队列结果，不把本地测试描述成跨设备验收。

## 6. 范围边界

本轮预计涉及回收站系列摘要 UI、重复系列恢复服务、`StorageService` 原子保存入口和对应测试。

本轮不做：

- 不提供“仅本期及以后批量恢复”。第26轮的部分删除会移动规则或缩短边界，当前数据不足以对所有旧系列无歧义地还原删除前规则；部分删除继续逐期恢复。
- 不恢复已彻底删除的记录，不改变物理删除和清空回收站语义。
- 不自动取消完成／跳过，不修改关联规划、专注、时间日志或提醒内容。
- 不允许根据模糊／重复规则猜测系列，不把系列恢复扩展为多个系列的批处理。
- 不改变普通待办恢复、团队待办权限或服务器协议，不修改其他现有未提交工作区文件。

## 7. 验收计划

1. **整系列恢复**：创建含历史、当前和未来期次的重复待办，完成／跳过部分期次，整组移入回收站；回收站摘要准确显示期次、日期范围和状态数量；确认后全部现存期次恢复，原状态与唯一重复规则保留。
2. **规则续跑**：恢复后执行一次重复维护，确认只产生预期的未来期次，不重复生成现有日期、不复活其他用户删除期次，且仍只有一个活动规则承载项。
3. **范围保护**：普通待办不出现整组入口；只有本期被删除或本期及以后被删除但保留期次仍活动的系列不出现整组入口；已有逐期恢复继续有效。
4. **异常旧数据**：缺失规则、多条规则、系列 ID 缺失／混乱和失效文件夹场景不错误批量恢复；失效文件夹仅影响该待办的分组归属，不丢失其它字段或期次。
5. **并发与失败**：确认前后系列成员或版本变化、重复提交及事务失败均不产生部分恢复；失败后所有原行仍在回收站并有可读反馈。
6. **分页与显示**：验证超过一页且规则承载项已删除的系列仍能补齐全部期次，展开、计数和恢复范围一致；验证搜索命中、手机窄屏、桌面、深色和大字模式；截图覆盖回收站摘要、确认界面和恢复后的列表。
7. 运行重复删除／恢复服务与存储测试、回收站 Widget 测试、相关静态分析和 Flutter Web release 构建；检查 `git diff --check`。
