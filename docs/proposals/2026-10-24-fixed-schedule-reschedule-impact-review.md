# 第39轮方案：固定日程改期后的关联事项复核

日期：2026-10-24（北京时间）

状态：**技术验收完成，待用户确认**

## 1. 建议与收益

考试、面试、预约等固定日程改期时，用户还需要判断关联待办的截止时间是否要调整、哪些规划块与新时间冲突，以及原有提醒会在何时再次触发。现有编辑器已按“仅本次／本次及以后／整个系列”计算实际改动范围，并检测日程与规划块重叠；确认界面主要说明系列范围和冲突数量，没有把关联待办和受影响规划放在一次清晰的改期复核中。

建议在现有保存确认流程中增加“改期影响复核”：根据最终选定的重复范围，展示旧／新日程时间、关联待办的当前状态和期限语义、与新日程重叠的规划块，以及保存后将采用的提醒时间。用户看清后显式确认保存。系统只提供事实与跳转入口，不替用户更改待办期限、规划或提醒设置。

产品语义依据见 [`todo-semantics.md`](../features/todo-semantics.md) 的“考试的关联表达”：考试改期后应提示复核关联待办和规划，不能静默移动已完成或正在执行的规划记录。

## 2. 当前实现依据

- `FixedScheduleEditorScreen._save` 已先按编辑范围构建准确的 `plan.changes`、`plan.active` 和 `plan.refreshItem`，再展示范围确认、运行冲突检测、调用 `saveFixedSchedulesIfUnchanged` 并重排固定日程提醒。
- 现有范围确认会提示系列影响场数；固定日程冲突检查能识别固定日程硬冲突和规划块软冲突，但冲突确认目前以数量和最多三条摘要呈现。
- 固定日程通过 `relatedTodoIds` 关联待办；详情页已有待办状态和期限的只读展示，待办详情已有反向查看关联日程的入口。
- `TodoItem` 的日期待办与具体时刻截止待办语义不同，二者都是截止目标而非时间占用；不能把截止晚于事件开始直接当成日历冲突。
- 固定日程提醒按每个场次的 `reminderMinutes` 相对开始时间生成；保存后现有 `ReminderScheduleService.scheduleFromStorage` 负责重新计算。改期不能新增第二套提醒所有权。
- 工作区当前另有 Android 到课提醒改动。第39轮提案、实现和提交应保留这些现有修改，不应纳入本轮。

## 3. 批准后的目标行为

### 何时显示复核

1. 仅编辑已有固定日程时检查改期影响；新建日程、只修改地点／备注／标题或只调整提醒配置时，沿用现有保存流程。
2. 用户确认本次编辑范围后，根据实际受影响的场次与原始快照比较日期、开始和结束时间。若任何受影响场次的日期或时间变化，且存在关联待办、重叠规划或已设置提醒，则进入复核。
3. “仅本次”“本次及以后”“整个系列”仍以现有范围计算为准。复核展示受影响场次数和日期范围；单次改期额外并列显示旧场次与新场次。不得把未受影响的较早场次误算进来。
4. 如果来源数据读取失败，明确说明无法完成影响检查并停止保存；用户可以重试或返回编辑。不能把失败当作“没有影响”。

### 复核页内容

1. **日程变化**：显示标题、范围、改期前后日期／时间与受影响场次数。仅日期待定或仅有开始时间的日程按真实精度显示，不补造结束时间。
2. **关联待办**：按 ID 去重后显示同一可见范围内、未删除待办的标题、完成／跳过／待处理状态和当前期限。日期待办标明“某天内完成”，定时待办显示具体截止时刻，未安排待办显示“未设置期限”。
3. 若关联待办的期限晚于新日程开始，标注“截止晚于日程开始，请核对”；这是提醒用户检查的事实提示，不代表待办与日程发生占用冲突，也不自动判定期限错误。
4. 已完成、已跳过的待办可作为历史上下文折叠展示；已删除或当前账号不可见的待办不显示标题。个人日程与个人待办关联；团队日程只显示同一团队的待办，团队 UUID 归一化规则与现有关系页面一致。
5. **冲突规划块**：列出与新日程时间实际重叠的规划标题、日期、交叠区间及状态；显示最多五项，超出时提供继续查看。只展示当前可见范围内的规划，并可跳转到现有规划详情／编辑入口。已完成、已结束、已取消等历史规划不得提示为待调整项目。
6. **提醒复核**：显示保存后每个有效提醒相对于新开始时间的触发时刻，例如“提前1天：10月28日 09:00”。不展示已经过去且不会实际触发的提醒为即将到来的通知，并说明原提前量配置会保留。
7. 复核页底部提供“返回修改”和“按此范围保存”。取消或返回不会写入日程、待办、规划或提醒注册表。

### 保存与导航

1. 用户确认后，沿用现有固定日程并发快照校验和保存；任何日程系列版本变化都拒绝保存并要求重新打开／复核。
2. 写入成功后沿用现有提醒重排和数据刷新流程。提醒重排失败应沿用当前应用的既有错误处理与重试策略，不应回滚已经成功保存的日程或重复创建通知。
3. 点关联待办进入现有 `TodoDetailScreen`；点冲突规划进入现有规划查看／编辑路径。返回复核页时重新读取数据；若来源变化，刷新内容并要求用户再次确认。
4. 用户选择保存后不自动调整任何待办期限、提醒提前量、规划块位置／状态、专注记录或固定日程关系。是否调整仍由用户在相应原有编辑器中完成。

## 4. 数据、安全与兼容边界

- 继续以 `FixedScheduleItem.relatedTodoIds` 为唯一日程—待办关系来源，不加待办外键、数据库字段、迁移、服务端接口或同步协议。
- 不将 due date 与固定日程视为互斥时间段；只有真实规划块和固定日程参加时段重叠检查。
- 复核只读，不自动写入关联对象；完成、跳过、进行中或已有实际投入的规划不被改写。
- 账号或团队范围变化、关联待办被删除、日程系列在复核期间更新时，清除旧可见数据、重新读取或拒绝保存；绝不短暂显示跨账号或跨团队标题。
- 外部手机日历来源的所有权规则保持不变；本轮不改写外部事件，不增加系统日历权限。
- Web、Android、iOS 与桌面端使用现有固定日程编辑器和提醒调度路径；本轮不声称完成跨设备服务端部署或真机通知验收。

## 5. 预计实施范围

- `lib/screens/fixed_schedule_editor_screen.dart`：在既有范围确认与冲突检测之间加入影响复核入口；采用独立、可滚动的复核面板，避免把过多文字塞进窄屏对话框。
- `lib/services/`：新增纯逻辑影响汇总 helper，按实际编辑范围比较场次、期限展示、冲突规划和提醒触发时间；精确处理关联 ID、重复场次和日期待定情况。
- `lib/storage_service_fixed.dart`、相关 Todo／规划查询契约：只在现有读取能力不足时增加一次性批量读取接口，明确返回读取失败，不进行逐项 N+1 查询。
- 现有详情／规划路由：复用并验证待办详情与规划详情跳转，不新建重复详情页面。
- 增加服务测试、存储范围测试和编辑器 Widget 测试；更新 `docs/features/todo-semantics.md` 的当前行为说明，并建立第39轮验收报告与图片证据。
- 避免全仓格式化；只运行变更文件格式检查、定向测试、静态分析、`git diff --check` 和 Flutter Web release 构建。实施验收时另做窄屏、深色、大字号布局检查。

## 6. 验收标准

1. 单次场次改期显示准确的旧／新日期与时间；仅修改文字或提醒时不出现不相关的改期复核。
2. 三种重复编辑范围只汇总实际受影响场次；此前保留场次、被逻辑删除的旧场次和新建场次均符合现有系列编辑语义。
3. 关联待办按精确 ID 去重、状态和期限语义正确；日期待办不会被显示成具体时刻，截止日期不会误判为时间占用。
4. 个人／团队和跨团队隔离成立；已删除、不可见待办的标题与地点不泄露；读取失败与空结果可区分。
5. 复核准确列出与新日程重叠的有效规划及交叠区间，历史规划不被要求改期；关联待办与规划入口进入正确详情。
6. 提醒预览使用当前配置和改期后触发时刻；取消复核保持旧日程和旧提醒，确认保存后由现有提醒调度更新一次。
7. 系列并发变化、账号切换、关联数据变化或读取失败不会以旧快照保存；用户返回修改时所有原编辑草稿仍保留。
8. 测试覆盖日期待定、无结束时间、跨日、时区／夏令时边界、过去提醒、重复范围和提醒重排错误；历史投入、专注、待办和关系未发生非预期写入。
9. 变更文件静态分析、格式、定向回归和 Web release 构建通过；提供至少一张改期复核页的手机截图及窄屏／深色／大字号检查结果。
10. 验收报告分别说明自动化、构建、截图来源、真机通知、在线服务与跨设备验证实际覆盖到哪里。
