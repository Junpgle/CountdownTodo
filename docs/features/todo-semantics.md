# 待办、固定日程、重复、习惯与时间语义规范

最后更新：`2026-07-20`

状态：`P0 产品语义已定稿；P1 持续收口；通用固定日程已接入能力协商式 debug/release 同步`

## 目的

本文定义 CountDownTodo 中待办、固定日程、重复待办、习惯、完成时间和规划块的产品边界。后续新增页、编辑页、AI 解析、提醒、统计、冲突检测、日历同步和多端同步都应遵循同一套语义。

本文是产品规则，不描述当前所有页面已经具备的行为。当前工作树已引入 `TodoTimeMode`，统一“未安排 / 日期待办 / 截止时刻”的新数据写入，并让解析、AI 上下文、日历和提醒策略使用该语义。`ItemSemanticsService` 会识别待办、固定日程和规划块；固定日程已有独立 `FixedScheduleItem` 和本地表，接入了手动/AI 确认、首页日程、进行中状态、系统日历、硬/软冲突、备份导入导出，以及独立 oplog 和 Alibaba 同步协议。同步协议通过 `fixed_schedules v1` 能力协商启用；旧服务端不会确认固定日程 oplog，也不会把缺失字段解释为云端删除。固定日程编辑器支持每天、工作日、每周、每月、每年和自定义天数的有限重复系列，保留自定义间隔与团队归属，并将每次发生物化为真实日程实例。同步冲突使用 `updated_at` 优先、版本号只处理同时间戳的严格 LWW；只有创建者能取消共享或跨团队转移日程。跨设备部署验证、跳过状态、习惯模型、真实提醒调度和关联待办编辑仍未完成。其余不一致内容应在后续阶段逐步落地，并保持旧数据兼容。

## 核心决策

1. **待办表示需要完成的结果，不表示一段被占用的时间。**
2. **重复是一种按周期产生待办实例的机制，不等于习惯。**
3. **习惯是用户主动开启的追踪方式，不能根据重复频率自动推断。**
4. **待办界面不再要求用户理解“全天事件”。** 用户只需选择“未安排”“某天内完成”或“具体时刻前完成”。
5. **日期待办不占用 24 小时。** 它可以在日历的全天区域展示，但不属于正在进行的活动，也不产生 24 小时时长。
6. **规划块表示实际预留的执行时段。** 把待办安排到 15:00–17:00，应创建规划块，而不是把待办本体改成两小时事件。
7. **固定日程表示由外部约束的时间段。** 考试、课程、面试、会议、航班、演出和预约等不能由用户自由挪动的事项，应归为固定日程，而不是待办或规划块。
8. **固定日程与规划块都占用时间，但可调整性不同。** 固定日程是硬约束，规划块是用户可以围绕硬约束调整的软安排。
9. **通用新增入口不擅自猜测日期。** 用户没有提供日期或时间时，新待办默认为未安排；从某个日期上下文创建时，可以继承该日期。
10. **新建重复待办必须有首次发生日期。** 没有具体时刻时，首次发生日期按日期待办处理。
11. **取件、取餐、取药等事项默认仍是待办。** “可领取时间—最晚领取时间”是待办的有效窗口，不表示整段时间被占用；取件码、地点和商家属于领域信息，不构成新的顶层事项类型。

## 统一术语

| 产品术语 | 定义 | 示例 | 不应理解为 |
| --- | --- | --- | --- |
| 普通待办 | 只需完成一次的任务 | 提交报名表 | 日历事件 |
| 重复待办 | 按规则产生多期实例的待办系列 | 每周五提交周报 | 自动等同于习惯 |
| 重复系列 | 共享同一重复规则的一组待办实例 | 7 月的四期周报 | 一个永远无法完成的大任务 |
| 本期 | 重复系列中当前需要处理的单个实例 | 本周五的周报 | 整个系列 |
| 习惯 | 用户明确选择持续追踪的行为 | 每天背单词 | 所有每日或每周待办 |
| 日期待办 | 有完成日期但没有具体时刻的待办 | 明天内取快递 | 持续一整天的活动 |
| 定时待办 | 有明确截止时刻的待办 | 明天 18:00 前交作业 | 15:00–17:00 的执行计划 |
| 取用类待办 | 需要领取、取回或签收某件物品的待办子类型 | 凭取件码领取快递 | 固定日程或新的顶层类型 |
| 固定日程 | 由外部确定日期或时间段、用户不能自由移动的事项 | 14:00–16:00 高数考试 | 需要勾选完成的任务 |
| 重复日程 | 按日程规则反复发生的固定事项 | 每周一 09:00 例会 | 重复待办系列 |
| 规划块 | 为待办预留的一段执行时间 | 15:00–17:00 写论文 | 新的重复待办实例 |

用户界面统一使用“重复”，不再使用“循环规则”“循环待办”“周期习惯”等混合称呼。代码、数据库和兼容工具中的 `recurrence`、`recurrenceSeriesId` 等内部名称暂不要求随产品文案修改。

“全天”只允许出现在以下技术或外部集成语境：

- 系统日历的全天区域或 all-day event 字段。
- 旧数据兼容、迁移和调试日志。
- 必须与系统日历术语保持一致的设置说明。

待办新增页、编辑页、卡片和普通帮助文案应使用“某天内完成”或“无具体时间”。

## 三类时间约束

判断一个事项属于什么类型，优先判断时间由谁决定以及用户是否需要勾选结果：

| 判断问题 | 待办 | 固定日程 | 规划块 |
| --- | --- | --- | --- |
| 核心含义 | 需要达成的结果 | 必须在指定时间发生或参加的事项 | 为完成待办主动预留的执行时段 |
| 时间由谁决定 | 用户或截止要求 | 学校、组织、预约方等外部来源 | 用户自己 |
| 是否可自由移动 | 截止前可以自行安排 | 通常不可自由移动 | 可以调整 |
| 是否需要勾选完成 | 是 | 否 | 记录执行状态，不等同于待办完成 |
| 是否占用日历时段 | 日期/截止本身不占用 | 是，属于硬占用 | 是，属于软占用 |
| 是否参与冲突检测 | 不参与时段冲突 | 参与，优先级最高 | 参与，遇到固定日程应建议改期 |
| 时间结束后的基础状态 | 可能完成或逾期 | 已结束 | 已完成、未执行或跳过 |

分类例子：

- “7 月 25 日 14:00–16:00 高数考试”是固定日程。
- “完成高数考试复习”是待办，截止时间可以设为考试开始前。
- “今晚 19:00–21:00 复习高数”是关联复习待办的规划块。
- “打印准考证”是待办，不是考试日程的一部分。
- “每周一 09:00 参加例会”是重复日程，不是重复待办。
- “每周五前提交周报”是重复待办，不是重复日程。

如果一句话同时包含多个意图，应拆分为关联对象，而不是压进一个待办。例如“下周五考试，今晚复习两小时”应产生一个固定日程、一个复习待办和一个关联规划块。

## 待办时间模型

### 未安排

- 用户只记录要做的事情，没有指定完成日期。
- 不因创建时间自动变成“今天的任务”。
- 默认不发送时间提醒。
- 可以进入收集箱、未安排分组或全量待办列表。
- 选择重复时必须先补充首次发生日期，因此未安排待办不能直接保存为重复系列。

### 某天内完成

- 用户指定完成日期，但没有指定具体时刻。
- 用户文案显示为“7 月 21 日内完成”或“今天内完成”。
- 在日历中可以放入全天区域，但不得计为 24 小时时长。
- 不进入“正在进行”“即将开始”等依赖时间区间的状态。
- 若启用提醒，使用绝对时刻；默认建议为目标日期 `09:00`，用户可以修改或关闭。
- 到目标日期结束仍未完成时，下一日开始判定为逾期未完成。

### 具体时刻前完成

- 用户指定明确的截止日期和时刻。
- 用户文案显示为“7 月 21 日 18:00 前完成”。
- 提醒相对截止时刻计算，默认建议为提前 5 分钟。
- 截止时刻已过且未完成时，判定为逾期未完成。
- 具体时刻只表达截止点，不表达用户会在此前持续执行。

### 可执行或有效窗口

- 部分待办只能在某个时间之后执行，并要求在另一个时间之前完成，例如“12:30 后可取餐，18:00 前取走”。
- 窗口开始表示“最早可以做”，窗口结束表示“最晚必须完成”，整段窗口不表示用户一直在执行。
- 有效窗口不占用日历网格，不参与时段冲突检测。
- 用户需要预留实际执行时间时，可以在有效窗口内创建规划块。
- UI 使用“12:30 后可取 · 18:00 前取走”等文案，不能显示为“12:30–18:00 持续进行”。
- 当前模型中的开始时间不能继续同时承担创建时间、可领取时间和日历占用开始时间；后续实现应通过统一语义层或独立字段消除歧义。

### 规划执行时段

- 需要表达“什么时候实际做”时，创建 `TodoPlanBlock`。
- 一个待办可以关联零个、一个或多个规划块。
- 规划块拥有开始时间、结束时间、计划时长、提醒和执行状态。
- 待办完成与规划块完成相关但不等价；规划块结束不应自动意味着待办目标已经完成，除非具体业务明确设置了自动完成规则。
- 已有待办被安排到具体时段时，不得复制出一个新的待办。

## 固定日程语义

### 适用范围

满足以下特征之一时，应优先识别为固定日程：

- 有明确开始和结束时间，且时间由学校、组织、预约方、交通服务或其他外部来源决定。
- 用户的核心意图是“参加、出席、到场、乘坐或等待事项发生”，而不是完成后勾选一个结果。
- 事项会真实占用日历时段，并应阻止同一时段继续安排规划块。

典型固定日程包括考试、课程、会议、面试、医生预约、航班、火车、演出和比赛。`CourseItem` 继续作为课程子类型；其他通用硬约束日程使用独立 `FixedScheduleItem`，不复用 `TodoItem.isDone` 或 `TodoPlanBlock`。

### 时间与状态

- 固定日程优先具有明确的开始和结束时间。
- 已确定日期但时间待定时，标记为“时间待定”，不能伪造 00:00–23:59 时间段。
- 只知道开始时间时，可以显示“结束时间待定”，不得自动补一小时。
- 基础状态为“未开始”“进行中”“已结束”“已取消”。
- “参加了”“缺席了”“考试成绩”等属于可选的参与结果或领域信息，不使用待办的 `isDone` 表达。
- 时间自然流逝到结束点后，状态变为“已结束”，无需用户勾选完成。

### 固定日程系列

- 课程、固定例会等可以形成重复日程系列。
- 重复日程共享时间规则，但每次发生是一个日程实例，不是待办实例。
- 有限重复系列必须保存首次日期和结束日期；每个实例共享系列 ID、重复规则和团队归属。
- 团队日程系列中的所有实例都应同步给团队成员，并作为相同优先级的硬时间约束参与冲突检测。
- 日程系列可以支持“仅本次”“本次及以后”“整个系列”的修改范围，但其完成率、逾期和习惯统计规则不适用。
- 考试通常是单次固定日程；同一科目的多次考试应作为独立日程或明确的考试系列，不能默认按周期复制。

### 冲突与优先级

- 固定日程属于硬时间约束，必须参与忙闲和重叠检测。
- 两个固定日程重叠时，提示硬冲突，由用户确认真实安排，系统不得自动移动其中任何一项。
- 规划块与固定日程重叠时，优先保留固定日程，并建议移动或拆分规划块。
- 日期待办和定时待办的截止点不占用时段，不与固定日程产生时段冲突。
- 课程表中的课程和通用固定日程应使用同一冲突语义。

### 考试的关联表达

考试通常需要同时连接多类对象：

- 固定日程：考试名称、开始/结束、地点、座位或考场、提醒。
- 待办：复习目标、携带材料、打印准考证等可勾选事项。
- 规划块：考试前各次复习安排。
- 倒数日：可以从考试开始时间派生展示，不要求用户重复维护一个相同日期。

考试改期时，应更新固定日程，并提示检查关联待办截止时间、提醒、倒数日和考试后的规划块；不得静默移动用户已经完成或正在执行的规划记录。

## 取件、取餐与物流类待办

### 默认分类

取件、取餐、领取报告、取药、取票和签收等事项，核心都是用户需要完成一个可勾选的结果，因此默认归为待办。它们可以作为“取用类待办”子类型承载专用展示和提醒，但不新增与待办、固定日程、规划块并列的顶层类型。

| 场景 | 分类 | 原因 |
| --- | --- | --- |
| 快递已放驿站，三天内领取 | 取用类待办 | 用户可在期限内自行选择时间 |
| KFC 餐品已好，凭 A056 取餐 | 取用类待办 | 需要完成领取动作，不占用固定时段 |
| 报告周五后可取，下周三前领取 | 带有效窗口的取用类待办 | 受到可领取时间和截止时间约束 |
| 预约 14:00 到柜台取证，迟到失效 | 固定日程 | 必须按外部指定时刻到场 |
| 15:00–17:00 快递上门，必须在家签收 | 固定日程或外部时间窗日程 | 用户必须在外部给定时段保持可用 |
| 快递已送达，今晚安排 20 分钟去取 | 取用类待办 + 规划块 | 领取结果是待办，20 分钟是自主安排 |
| 电影 19:30 开场，提前取票 | 电影是固定日程，取票是关联待办 | 固定发生时间和准备动作应分开 |

判断关键不是标题中是否出现“取件”或“取餐”，而是用户能否在窗口内自由选择执行时刻。可以自由选择的是待办；必须按预约时刻到场的是固定日程。

### 时间和状态

- 尚未可领取：待办处于等待条件满足的状态，不是正在执行。
- 已可领取：待办变为可执行，可以触发一次“已可领取”通知。
- 已领取：用户完成待办。
- 已过期：超过领取截止时间仍未完成；表现为逾期或领域状态“已过期”。
- 已取消：订单、预约或物流流程取消，不能通过“已完成”伪装。
- 仅收到取件码但没有可靠日期时，不得默认今天全天；应使用来源时间、明确的有效期，或请求用户确认。
- 来自当前订单通知且能可靠确认当天可领取时，可以设为“今天内完成”，但必须在确认页展示该推断。

### 领域信息

取用类待办可以附带以下信息，但这些信息不改变其待办身份：

- 取件码、取餐号或核销码。
- 商家、快递公司、驿站或柜台名称。
- 领取地点和导航信息。
- 订单号、运单号或来源应用。
- 可领取时间、最晚领取时间和订单状态。
- 原始截图或通知来源。

取件码、取餐码和订单号属于敏感信息：

- 标题中不直接拼接完整码值，应放入结构化字段或受保护的详情区域。
- 锁屏通知、桌面组件和灵动岛默认遮盖部分字符，用户解锁或主动展开后再显示完整内容。
- 不应仅为了跨端展示而把本地截图或完整敏感码上传到云端。

### 提醒和实时展示

- “已可领取”是一次状态提醒，不应通过“全天待办”模拟。
- 有明确过期时间时，可以增加相对过期时间的提醒。
- 只有日期没有具体过期时刻时，使用日期待办的固定时刻提醒。
- 餐品已好等短时效事项可以在灵动岛或高优先级区域持续展示到领取或失效，但其状态名称应为“待领取”，不能显示为“全天进行中”。
- 实时状态变化来自可信订单或物流来源时，应更新同一待办，不能反复创建重复待办。

## 时间输入与默认规则

| 输入或入口 | 目标时间模式 |
| --- | --- |
| 在通用新增页输入“买牛奶” | 未安排，不猜测今天 |
| 在 7 月 21 日的日期上下文创建“买牛奶” | 7 月 21 日内完成 |
| “明天取快递” | 明天内完成 |
| “明天 18 点前交作业” | 明天 18:00 前完成 |
| “明天下午三点到五点写论文” | 创建或关联“写论文”待办，并创建 15:00–17:00 规划块 |
| “明天下午三点到五点高数考试” | 15:00–17:00 固定日程，并占用该时段 |
| “下周一开会，时间待定” | 下周一的固定日程，标记时间待定 |
| “每周一上午九点例会” | 每周重复日程，不生成可勾选待办 |
| “每周五交周报” | 重复待办；要求确认首次周五；不是习惯 |
| “每天 9 点吃药” | 每天重复的定时待办；截止/提醒时刻为 09:00；不是自动习惯 |
| “顺丰已到驿站，取件码 8866，周三前取” | 周三内完成的取用类待办，保存取件信息 |
| “KFC A056 已出餐” | 已可领取的取用类待办；可靠当前来源可推断今天，但需展示确认 |
| “明天 14:00 预约取证” | 固定日程；若另有材料准备，再建立关联待办 |

如果自然语言只有“上午”“下午”“晚上”等模糊时段，解析器不得静默捏造精确时刻。应保留为日期待办并提示补充时间，或者根据已有的、明确展示给用户的偏好设置转换。

## 重复待办语义

### 系列与实例

- 用户创建的是一套重复规则和第一期待办。
- 系统按规则产生后续实例；每期拥有独立的完成、逾期和跳过状态。
- 用户在主列表中主要看到当前可执行的一期，不应看到大量未来实例堆叠。
- 历史和未来实例可以在系列详情或进度视图中查看。
- 完成本期只完成当前实例，不结束重复系列。
- 结束重复只阻止后续实例产生，已完成和历史实例必须保留。

### 重复规则

首批产品规则继续支持：

- 每天
- 每个工作日
- 每周
- 每月
- 每年
- 每隔若干天

后续可以增加每周多个指定星期、按次数结束等规则，但不得改变现有规则的含义。

开放式重复与有限重复都合法：

- 开放式重复：没有预设结束日期。
- 有限重复：在指定日期或指定次数后结束。
- UI 必须明确显示“永不结束”或实际结束条件，不能用空值让用户猜测。

### 修改和删除范围

修改重复待办时，必须明确选择影响范围：

1. 仅本期。
2. 本期及以后。
3. 整个系列。

删除使用同样的范围选择。“整个系列”删除历史记录属于高风险操作，默认不选中，并需要二次确认；普通的“结束重复”只停止未来实例。

### 完成、逾期与跳过

- `已完成`：本期目标已经完成，不因完成早晚改变这个事实。
- `逾期未完成`：本期截止边界已过，且没有完成或跳过。
- `已跳过`：用户主动声明本期不执行；既不算完成，也不算逾期未完成。
- 重复任务统计至少分别展示完成、逾期未完成、跳过和进行中数量。
- 在系统没有可靠完成时间戳前，统计只能称“完成率”，不能称“按期完成率”。
- 可以展示“连续完成 N 期”，但不得据此把该系列称为习惯。

## 习惯语义

P0 不新增习惯数据模型，也不把任何现有重复系列自动迁移为习惯。

未来如果建设习惯功能，必须满足：

- 用户主动选择“作为习惯追踪”；默认关闭。
- 不能仅根据标题、每天重复或完成次数自动推断习惯。
- 习惯可以拥有目标次数、目标数量、补打卡、请假/冻结、连续记录等专属能力。
- 只有明确作为习惯追踪的系列才能进入“习惯完成率”“习惯连续天数”等统计。
- 每周交周报、每月还款、定期缴费等周期工作默认保持为重复待办。

在习惯模型落地前，现有界面中的“周期习惯”“习惯完成率”“坚持 N 期习惯”等文案应改为“重复待办”“完成率”“完成 N 期重复任务”等中性表达。

## 提醒规则

提醒必须与时间模式一致：

| 时间模式 | 默认提醒 | 允许的提醒方式 |
| --- | --- | --- |
| 未安排 | 关闭 | 用户先补充日期或显式创建独立提醒 |
| 某天内完成 | 当天 09:00 | 当天固定时刻、关闭 |
| 具体时刻前完成 | 提前 5 分钟 | 准时、提前若干分钟/小时/天、关闭 |
| 固定日程 | 相对开始时间，默认提前 15 分钟 | 一个或多个相对开始时间的提醒、关闭 |
| 取用类待办 | 可领取时提醒一次；有期限时追加过期前提醒 | 状态提醒、固定时刻、相对过期时间、关闭 |
| 规划块 | 提前 5 分钟 | 相对规划块开始时间、关闭 |

日期待办不得通过“23:59 前 5 分钟”模拟提醒。通知、桌面摘要和灵动岛可以在当天展示日期待办，但必须有去重策略，且不能把它标记为持续进行中的事件。

考试等重要固定日程可以建议“提前 1 天”和“提前 30 分钟”等多级提醒，但所有提醒必须在保存前清晰展示，不得只根据标题静默增加通知。

## 展示与统计规则

### 待办卡片

- 未安排：显示“未安排”。
- 日期待办：显示“今天内”“明天内”或具体日期，不显示“全天”。
- 定时待办：显示截止时刻和“前完成”。
- 重复待办：显示可读规则和“本期”，例如“每周五 · 本期今天截止”。
- 取用类待办：显示“待领取”、地点、有效期；敏感码默认遮盖。
- 习惯标记只在用户明确开启习惯追踪后出现。

### 日历与今日视图

- 日期待办可以展示在日历全天区域，但产品语义仍是“当天内完成”。
- 日期待办不阻塞日历时段，不参与忙闲冲突计算。
- 固定日程进入具体时间网格，作为不可自动移动的硬占用。
- 规划块进入具体时间网格并参与时间冲突判断。
- 固定日程与规划块重叠时，优先提示调整规划块。
- 多日长期待办只保留一个截止日期，不应横跨多天占满全天区域；实际推进通过多个规划块表达。

### 统计

- 普通待办统计完成数量、未完成数量和完成率。
- 重复待办按实例统计完成、逾期未完成、跳过和进行中。
- 重复系列可以统计连续完成期数，但使用中性表述。
- 习惯统计必须等待显式习惯模型落地。
- 日期待办不贡献 24 小时计划时长或专注时长。
- 固定日程可以统计场次和占用时长，但不进入待办完成率、重复待办完成率或习惯统计。
- 规划时长和实际专注时长继续来自规划块和番茄钟记录。

## AI 解析规则

AI、规则解析器、图片识别和聊天 action 必须遵循相同语义：

1. 用户没有提供日期和时间时，输出未安排，不得默认今天全天；只有可靠的当前订单、通知或创建入口上下文可以提供明确日期。
2. 用户提供日期但没有具体时刻时，输出日期待办。
3. 用户提供截止时刻时，输出定时待办，不得自动补出一小时执行区间。
4. 考试、课程、会议、面试、预约、航班等由外部时间约束的事项，应输出固定日程；有开始和结束时间时不得降级为定时待办或规划块。
5. “复习高数”“准备面试”等表示需要完成的目标时，输出待办；用户指定自主执行时段时，再建立关联规划块。
6. 无法判断一个时间段是外部固定安排还是用户自主计划时，必须确认“这是固定日程，还是可调整的计划时间？”。
7. 只有“每天”“每周”“每个周几”“每月”“每年”“每隔 N 天”“工作日”等持续性表达才能创建重复规则。
8. 重复表达还必须区分重复待办和重复日程：“每周五前交周报”是重复待办，“每周一 9 点例会”是重复日程。
9. “下周一”“这周五”“下个月 1 号”表示单次日期，不是重复。
10. 重复待办默认不是习惯；在习惯模型落地前，AI 不得输出习惯类型。
11. 把已有待办安排到具体时间段时，使用 `create_plan_block`，不得复制或改写为新的定时待办。
12. 识别到取件码、取餐码、核销码、驿站或“已出餐”等信息时，默认输出取用类待办，并提取可领取状态、有效期、地点和码值；不能仅因有时间信息就归为固定日程。
13. 取用事项只有在必须按预约时刻到场时才归为固定日程；若只是可领取窗口，保持为待办。
14. 当前通知或订单截图可以使用可靠的来源时间辅助判断“今天”，普通文本不得无依据推断日期。
15. 解析结果进入保存前，应以用户可读方式展示对象类型、时间语义、有效窗口和重复规则，供用户确认。

## 兼容和迁移约束

P0 不修改代码、数据库或同步协议。后续实现必须遵守：

- 保留 `RecurrenceType`、`recurrenceSeriesId`、`isAllDay` 等旧字段的读写兼容。
- 旧数据可以通过显式字段和 00:00–23:59 等历史时间范围推断为日期待办。
- 新数据应由统一入口明确写入时间模式，不能继续依赖不同页面各自推断。
- 不得为了改文案重建重复系列或更换系列 ID。
- 不得把现有重复系列批量标记为习惯。
- 日历同步仍可把日期待办写成标准全天事件。
- 当前 `CourseItem` 继续作为课程类固定日程使用；引入通用固定日程模型时不得破坏既有课程数据和课表行为。
- 不得通过自动迁移把历史定时待办批量改成固定日程；只能根据明确来源或用户确认逐项转换。
- 固定日程必须保留开始/结束、取消状态和外部来源信息；不能复用待办完成字段代替日程状态。
- 取件码、取餐码等旧数据可以继续从备注读取，但新实现应逐步使用结构化领域信息，并保持旧客户端可读。
- 特殊通知和灵动岛展示不得继续把 `isAllDay` 当作“待领取”的代理条件。
- 敏感码的云同步、通知和桌面展示必须经过隐私审查；默认不上传原始截图。
- Windows、Android、Web 和 macOS 必须得到一致的待办时间模式；平台专属展示只能建立在统一语义之上。
- 通用固定日程使用独立 `fixed_schedules` 表和独立 oplog；不能写成旧待办实体，也不能复用待办同步字段。
- 客户端只有在服务端明确声明 `fixed_schedules v1` 后才确认固定日程 oplog。旧 Alibaba/Cloudflare 服务端忽略未知请求字段时，本地记录和 oplog 必须继续保留。
- 首次连接支持该能力的服务端时，客户端应上传全部本地固定日程并请求该实体全量下行，避免复用旧共享水位线造成漏传。
- 新后端能力先在外部 Alibaba debug 服务目录开发并完成兼容协商；只有收到明确发布同步请求后才复制到生产目录，且不得破坏现有 Cloudflare 兼容行为。

## P1 输入与完成标准

P1 只负责统一底层语义和现有入口行为，不建设习惯中心，也不进行新增页的大规模视觉改版。通用固定日程使用独立模型、持久化和同步协议，不复用 `TodoItem`；当前纵向切片、有限重复系列、团队归属和 debug 协议已经实现，后续阶段继续完成部署验证、提醒、重复系列的分范围编辑和显式关联待办编辑。

P1 至少应完成：

- 建立统一的待办时间模式解析与格式化入口。
- 建立待办、固定日程、规划块的统一意图分类规则；AI 在无法分类时要求确认。
- 将取件、取餐和物流状态识别为待办领域信息，不再依赖全天状态触发特殊展示。
- 手动新增、批量新增、AI 新增、确认页和编辑页一致保存日期待办状态。
- 清理业务层重复的全天推断，保留一个兼容入口。
- 统一通知、日历同步、今日全天区域和进行中活动对日期待办的判断。
- 将个人时间线中的习惯文案改为重复待办的中性文案。
- 为旧数据推断、JSON 往返、所有新增入口、通知边界和日历同步补充测试。
- 为取件码识别、有效窗口、状态提醒、通知去重和敏感信息遮盖补充测试。
- 未收到明确发布同步请求时不修改外部生产目录 `CDT-server/math_quiz_backend/`；始终不得破坏既有重复系列 ID 和 Cloudflare 兼容行为。

通用固定日程落地阶段至少应完成：

- 设计独立于 `TodoItem` 和 `TodoPlanBlock` 的固定日程模型，以及单次日程和日程系列的关系。
- 复用或兼容现有 `CourseItem` 的硬时间约束、日历展示和冲突语义。
- 支持未开始、进行中、已结束、已取消，以及时间待定和结束时间待定。
- 支持提醒配置、地点、备注、来源、时区、能力协商式多端同步和逻辑删除；真实提醒调度另行验收。
- 支持固定日程与规划块的硬/软冲突检测。
- 支持考试与待办、规划块、倒数日之间的显式关联，避免复制日期。
- 先在外部 Alibaba debug 服务目录完成后端开发、能力协商和跨设备验证，再按明确发布请求同步生产目录。

P1 验收时，现有待办场景必须在手动、AI 和编辑流程得到一致结果；固定日程相关输入至少必须被正确识别和确认，不能再被静默归为习惯或可自由移动的规划块。
